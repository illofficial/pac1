# 111C — прототип онлайн-мастеринг сервиса + iOS-обёртка

Вставляешь ссылку на YouTube-видео → сервис извлекает аудиодорожку →
прогоняет через фирменную DSP-цепочку (`mastering_chain.py`) → отдаёт WAV,
16 бит / 44100 Гц. Бесплатно — 1 трек/день до 3 минут; по подписке Pro —
до 30 треков/день до 10 минут, оплата через Apple In-App Purchase.

## Что внутри

```
mastering-service/
├── backend/
│   ├── main.py               FastAPI: задачи, статус, отдача файла, подписка
│   ├── extraction.py          Извлечение аудио из YouTube через yt-dlp
│   ├── jobs.py                 In-memory очередь задач + модель статусов
│   ├── storage.py              Временное хранилище WAV + авто-очистка по TTL
│   ├── subscriptions.py        Paywall: проверка подписи Apple, лимиты тарифов
│   ├── certs/                  Apple root-сертификаты (нужно скачать - см. certs/README.md)
│   ├── mastering_chain.py      DSP-цепочка
│   └── requirements.txt
├── frontend/
│   ├── index.html               Один экран: ссылка -> статус -> скачать
│   ├── style.css
│   └── app.js                   Поллинг статуса, мост с iOS-обёрткой
└── ios-app/                     Xcode-проект (Swift, WKWebView, StoreKit 2)
    ├── README.md                 Пошаговая настройка - см. отдельно
    └── MasteringApp/              Исходники для добавления в новый Xcode-проект
```

## Запуск бэкенда локально

Нужны: Python 3.10+, и **ffmpeg**, установленный в системе (yt-dlp
использует его, чтобы конвертировать аудио в WAV) — `pip` его не ставит.

```bash
# ffmpeg (если ещё не стоит)
# Ubuntu/Debian:  sudo apt install ffmpeg
# macOS:          brew install ffmpeg

cd mastering-service/backend
pip install -r requirements.txt

uvicorn main:app --reload --port 8000
```

Открой `http://localhost:8000` — фронтенд отдаётся тем же сервером.

## Как это устроено внутри

1. `POST /api/jobs` принимает ссылку, проверяет лимит длины (10 мин) через
   `yt_dlp.extract_info` **до** скачивания, создаёт задачу и запускает её в
   фоне (`BackgroundTasks`), сразу возвращая `job_id`.
2. Фронтенд поллит `GET /api/jobs/{id}` каждые 1.5 сек и подсвечивает
   channel strip (IRON → ENHANCER → MULTIBAND → LIMITER) по колбэку
   `on_stage`, который теперь есть в `mastering_chain.process_audio` —
   это реальные стадии твоей цепочки, а не выдуманный прогресс-бар.
3. Когда готово, `GET /api/jobs/{id}/download` отдаёт файл. Название
   берётся из заголовка видео.
4. Тариф определяется по заголовку `X-Device-Id` (его подставляет iOS-
   обёртка через `WKUserScript`, см. `ios-app/`). Обычный браузер без
   обёртки генерирует свой ID в `localStorage` — работает, просто без
   возможности оформить Pro (там нет StoreKit).
5. После покупки в приложении оно шлёт подписанную Apple-транзакцию на
   `POST /api/subscription/verify` — бэкенд проверяет подпись через
   официальную `app-store-server-library` и на её основе включает Pro для
   этого `device_id`. Подробности — `ios-app/README.md`, разделы 4-6.

## Что нужно знать перед реальным запуском

Это прототип, который честно демонстрирует поток, но кое-что упрощено
специально, и в проде нужно заменить:

- **Очередь задач.** Сейчас — словарь в памяти процесса + `BackgroundTasks`.
  Как и планировалось в исходном обсуждении архитектуры, для реальной
  нагрузки нужен Celery/RQ + Redis: словарь в памяти умирает при рестарте
  сервера и не масштабируется на несколько инстансов.
- **Хранилище.** Сейчас — локальная папка `backend/storage/` с TTL-очисткой
  раз в 15 минут (по умолчанию файлы живут 3 часа). Для прода — S3-совместимое
  хранилище с lifecycle-правилом, как в исходном плане архитектуры.
- **Rate limiting.** Сейчас — счётчик активных задач по IP в памяти
  (не больше 2 одновременно). Это защищает от одного человека, но не от
  распределённой нагрузки — в проде нужен нормальный rate limiter (Redis).
- **CPU-масштабирование.** DSP-обработка (`mastering_chain.py`) — CPU-bound
  и синхронная. Сейчас она блокирует один воркер `BackgroundTasks` на всё
  время обработки трека. При реальной нагрузке — выносить в отдельный пул
  процессов/воркеров, как и предполагалось изначально.
- **Подписка привязана к устройству, не к аккаунту.** `subscriptions.py`
  хранит подписку по `device_id` из Keychain — переустановка/смена телефона
  требует Restore Purchases в приложении. Для полноценного мульти-девайс
  сценария нужен настоящий логин — см. `ios-app/README.md`, раздел 7.
- **Не проверено вживую в этой песочнице.** У среды, где я это собирал, нет
  сетевого доступа к youtube.com (разрешён только узкий список доменов вроде
  pypi/npm/github), поэтому реальное скачивание с YouTube через `yt-dlp` я
  проверить не мог. Весь остальной поток — создание задачи, поллинг статуса,
  переключение стадий, финальные метрики (LUFS/true peak), скачивание,
  формат файла (16 бит/44100 Гц), лимиты бесплатного/Pro тарифа — прогнан
  end-to-end с тестовым аудио вместо реального YouTube-видео и работает.
  iOS-часть (Swift/StoreKit2/WKWebView) я не мог скомпилировать вообще —
  в этой среде нет macOS/Xcode/iOS SDK, код написан по официальному API
  максимально аккуратно, но первую сборку в Xcode стоит сделать внимательно.
  Стоит один раз прогнать всё на реальной ссылке и реальной sandbox-покупке
  перед тем, как показывать кому-то ещё.

## Юридический нюанс (напоминание)

Скачивание аудио с YouTube нарушает условия использования площадки, даже
если файл дальше обрабатывается и меняется. Это не блокирует прототип, но
несёт реальный риск при публичном запуске — см. более подробное обсуждение
в исходном конспекте проекта.
